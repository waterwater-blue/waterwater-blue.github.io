用 Wireshark 抓取自己的 QQ 流量：它到底走 TCP 还是 UDP？加密了吗？能还原出明文文件吗？

发表于2026-10-18|更新于2026-10-18|网络分析
|浏览量:

抓包是网络分析的入门功夫。装好 Wireshark，双击网卡，点击”开始”，看着屏幕上滚动的数据包，很多人会有一种”我能看见互联网了”的错觉。

但真正有意思的问题不是”我看到了什么”，而是三个追问：

  1. QQ 到底用 UDP 还是 TCP？
  2. 它的通信是加密还是明文？
  3. 如果是明文，能不能把传输的文件原样捞出来？

网上关于第一个问题的答案两极分化。有人信誓旦旦”QQ 用 UDP 8000 端口”，也有人说是 TCP。到底谁对？

我用自己的电脑和手机做了两组抓包，尝试回答这三个问题。结论是：第一个问题的流传版本已经过时，第二个答案是”加密”，第三个问题的答案取决于一个容易被忽略的前提。

隐私声明：本文所有抓包均基于本人自有账号、本人设备，在本人局域网内完成。文中 IP、域名等可能定位到个人网络的信息已做脱敏处理，未包含任何聊天内容、账号信息或第三方通信数据。

一、实验环境与方法

项目 配置
操作系统 Windows 11
抓包工具 Wireshark 4.x
PC 端 QQ NTQQ 9.9.x
手机端 QQ 8.9.x
网络环境 校园网（WLAN）

抓包方法本身没什么讲究：双击首页的 WLAN 网卡开始抓包，在抓包过程中依次执行发文字消息、发图片、传小文件等动作，然后停止并保存为 pcapng 文件。关键动作要在抓包窗口打开时进行，否则对应的流量不会被记录。

一个重要的经验：抓包前要先定位 QQ 连接的目标 IP，否则数据包列表里混着浏览器、系统更新、游戏等各类流量，难以分辨。可以用 PowerShell 查出 QQ 进程的实际连接：

输出的结果指向腾讯自有网段（脱敏记作 A.B.C.D，端口 443），这些就是后续过滤的依据。

二、问题一：UDP 还是 TCP？

结论：TCP。

用 tcp.port == 443 作为显示过滤器，Wireshark 筛选出 22 个相关数据包。

从数据包列表的 Protocol 列可以看到，这 22 个包全部是 TCP，目标端口一致为 443（即 HTTPS 的标准端口）。

为了排除”可能存在其他传输方式”的可能，我又用 udp.port == 8000 这个老教程中常见的过滤器做了对照。结果是：没有任何数据包被匹配上。

这一点值得特别说明。搜索”QQ 抓包”会看到大量教程声称 QQ 使用 UDP 8000 端口，并给出 0x02 开头、0x03 结尾的包结构示例。这个描述对应的是 OICQ老协议，大约活跃在 2008 至 2015 年间。那时的 QQ 登录默认走 UDP 8000，UDP 被封锁则回退到 TCP 443。现代版本已经把这套协议替换掉了，老客户端里”在线传输方式 TCP/UDP”的选项如今也已消失。

换句话说，照着老文章去抓 UDP 8000 会一无所获——这不是操作失误，而是那些资料已经过时了。

关于本机的网络环境：抓包显示本机地址为脱敏后的校园网内网地址，服务器地址为腾讯公网地址。所有流量均指向腾讯服务器，没有出现两台设备直接互连的情况。这与校园网的用户隔离策略有关——同一网段内的设备禁止互访，因此 QQ 的 P2P 直连无法建立，消息只能经服务器中转。

这个现象恰好回应了课程里”计算机与计算机之间的通信真的发生在两台计算机之间吗”这个追问：大多数时候，答案是否定的。 所谓的”点对点”只是协议层面的一种优化尝试，成不成立取决于网络环境。

三、问题二：加密还是明文？

结论：加密，且是 TLSv1.3。

在筛选出的数据包上右键选择「追踪流 → TCP 流」，Wireshark 会把该 TCP 连接的所有分段按序拼接，并尝试解析应用层协议。

追踪流窗口内的信息给出了明确答案：

  • Protocol 列显示 TLSv1.3
  • Info 列记录了完整的握手与加密过程：Client Hello (SN=xxx.tencent.com) → Server Hello, Change Cipher Spec → Application Data

这里有几个值得解读的细节：

SNI 域名是明文的。 追踪流的十六进制视图里能直接读出 xxx.tencent.com 这样的域名。这是 TLS 握手的 Client Hello 阶段明文携带的，用于服务器选择——它无法加密，否则服务器不知道该把连接交给谁。

握手完成后全是乱码。 从 Change Cipher Spec 开始，双方协商出会话密钥，后续所有 Application Data 都是密文。在十六进制视图里表现为完全不可读的二进制。

列表中出现的 Illegal Segments 提示属于正常现象。这是因为抓包点不在数据通路上游，部分数据包已被网卡硬件卸载或分段处理，Wireshark 无法完整重组。遇到这种情况不必修改抓包设置。

于是，这次抓包能得到什么、看不到什么，也就清楚了：

抓包能看到的 抓包看不到的
通信对端的 IP 地址 聊天文字内容
SNI 域名（如 xxx.tencent.com） 图片的具体内容
通信时间与频率 传输的原始文件名
传输字节数与流量方向 文件的实际数据

一句话：抓包让你看见”谁在什么时候和你说了多久话”，看不见”说了什么”。这正是 TLS 存在的意义。

四、问题三：能否恢复出明文传输的文件？

4.1 方法原理

不同文件类型有固定的文件头特征码（magic number），可以作为文件开始的标志：

文件类型 十六进制特征码
JPEG FF D8 FF
PNG 89 50 4E 47
GIF 47 49 46 38
ZIP 50 4B 03 04
PDF 25 50 44 46

在 Wireshark 里追踪 TCP 流，只要载荷未被加密，就能用 Ctrl+F 在十六进制视图中搜索这些特征码，定位文件在字节流中的起点，删除之前的协议头部分，剩下的即为文件本体。

这个方法成立有两个前提：① 载荷未加密；② 数据在同一条 TCP 流内。

4.2 实际尝试：全部失败

我在抓包中逐一搜索了上述特征码。

搜索 JPEG 的 FFD8FF，搜索框变红，未找到。

搜索 PNG 的 89504E47，同样是未找到。

搜索 ZIP 的 504B0304，依然未找到。

三次搜索全部失败。

原因不神秘：TLS 已经把这些字节彻底加密成了随机数据。在密文里搜索文件特征码，等于在一堆随机数中寻找规律——文件特征码是明文世界的产物，密文中不存在这个概念。

这也解释了一个常见的网络传言。早期 QQ 协议使用 TEA 算法加密消息体，而 TEA 是对称加密。这意味着：只要拿到会话密钥，所有流量都可以被解密。而登录请求包在协商密钥之前就已发出，其中的密码摘要容易被离线暴力破解——破解者的本机运算速度可达每秒 10^6 至 10^8 次尝试。

这套攻击链条依赖的是弱加密与可离线验证的口令摘要。 现代版本全面转向 TLS 之后，这条路已经被堵死：没有密钥无法解密，而密钥交换本身由 TLS 的密钥协商机制保护。

结论是：在当前 QQ 版本上，”从流量中恢复出明文文件”这条路是走不通的。 这不是技巧问题，是加密的预期效果。

4.3 一次失败实验的记录

值得记录的是，特征码搜索并非在一开始就顺利的。

最初的两次抓包几乎一无所获——数据包列表里全是长度 55 至 66 字节的包。查阅协议字段后确认，这些是TCP 层的 Keep-Alive 保活包，只用于维持连接，不携带任何应用层数据。

原因很简单：抓包期间并没有真正收发任何消息。抓包是一个需要”配合”的动作——必须在数据包被捕获的瞬间产生流量，否则抓到的只有网络的心跳。

第三次调整了顺序：先启动抓包，再执行发送操作，终于捕获到了真实的载荷。

这条 Len=406 的数据包来自某个 HTTP 服务（端口 80），说明同一份抓包文件中同时存在不同应用的不同传输方式：有的走加密的 443，有的走明文的 80。

这个观察引出另一个问题：同一台机器上，哪些流量是加密的，哪些是明文的？

Wireshark 的过滤器给出了一个粗略答案。用 QQ 服务器的 IP 做过滤并加上 tcp.len > 100 的条件后，筛选结果与之前的对照形成了鲜明反差：

流量类型 协议栈 内容可读性
QQ 通信 TCP/443 + TLSv1.3 握手后全为密文
某些网页服务 TCP/80 + HTTP 响应头与正文均可直接阅读

结论是：是否加密取决于具体应用，QQ 属于强制加密的那一类。 这也意味着，如果要演示”从流量中还原文件”这一手法，就不能选 QQ 作为样本——需要另找一个明文传输的场景。

4.4 明文场景的验证尝试

为了验证特征码方法本身的有效性（而非仅仅展示一次失败），我在本机搭建了一个明文 HTTP 文件服务作为对照：

服务正常启动后，浏览器访问确实能看到文件内容——说明文件服务本身工作正常，文件确实以明文形式传输。

然而后续抓包却一无所获，这段排查过程本身很有价值，记录三个关键发现：

其一，环回接口的流量不经过物理网卡。 最初通过 127.0.0.1:8080 访问，Wireshark 上完全没有对应流量。原因是环回（loopback）接口的数据在操作系统内核内部直接传递，不会流出到物理网卡。这是抓包的一个基本边界——抓包点必须落在流量实际经过的网卡上。

其二，本机地址可能被防火墙拦截。 改用局域网地址 10.34.x.x:8080 访问后，连接被拒绝，说明该端口未在防火墙上放行。

其三，虚拟网卡是另一条独立通道。 本机装有 VMware，其虚拟网卡地址与 WiFi 地址属于完全不同的网络栈。从哪个地址发起访问，流量就走哪张网卡，用 Wireshark 抓错网卡自然一无所获。

这三点合在一起说明了一件事：抓包不是”打开软件就有数据”，而是要先想清楚数据会经过哪条路径。 环回、虚拟网卡、物理网卡，Windows 上的网卡绑定与优先级设置，每一环都可能让流量”消失”。

五、PC-PC 端与 PC-手机端对照

作业要求覆盖两类场景。在校园网环境下，手机 QQ 与电脑 QQ 的通信能够正常建立，抓包结果与 PC-PC 场景一致：

观察点 PC-PC 端 PC-手机端
建连方式 尝试 P2P，失败则经服务器中转 同左
传输层协议 TCP TCP
目标端口 443 443
加密方式 TLSv1.3 TLSv1.3
可见信息 IP、端口、字节数、SNI 同左

两点补充说明：

关于 P2P 直连。 同一局域网下抓包时，如果能看到 QQ 直接连向对方 IP 的随机高位端口，说明 P2P 打洞成功。本次实验中未观察到这种情况，因为校园网的用户隔离策略阻止了同网段设备互访，所有流量都指向腾讯服务器。作为对照，在家庭网络环境下通常可以观察到直连流量。

关于图片与文件的落点。 手机端发送的图片，多数情况下是先上传到腾讯的 CDN 节点，再把URL 发送给对端，而不是直接在两台设备之间传输。这解释了为什么抓包时看到的是大量到 qpic.cn 相关地址的连接。

六、三个问题的答案汇总

问题 答案
UDP 还是 TCP TCP，端口 443。UDP 8000 属 2008–2015年老协议，已淘汰
加密还是明文 加密，TLSv1.3。握手后全部为密文，仅 SNI 域名明文
能否恢复明文文件 在 QQ 流量下不能。特征码搜索全部失败，原因是 TLS 加密

补一句关于第三问的说明：特征码方法本身是有效的，它失败的原因是加密破坏了两个前提之一（载荷未加密）。这与”用钥匙能开门，但门被锁住了”是一个道理——方法没错，是对象选错了。 若要演示这一手法，应当选择明文传输的场景（如 HTTP 下载），而非加密的即时通讯。

七、一点感想

这次抓包最反直觉的收获，是那些流传甚广的”标准答案”有多不可靠。

“QQ 用 UDP 8000”——错，那是十几年前的老协议，照着做只会一无所获。
“抓包能看到聊天内容”——错，现代通信全程加密，能看到的只有元信息。

这两点都不是”我错了”，而是资料没有跟上技术演进。做网络分析时，动手验证的价值远大于采信二手结论。一个 udp.port == 8000 过滤器花不了三秒，但它比任何一篇十年前的文章都更能说明问题。

另一个收获来自那些失败。抓不到保活包以外的数据，是因为抓包时没有真正收发消息；访问本地服务抓不到流量，是因为流量没走那张网卡。每一次失败都指向一个更基础的问题——数据到底在哪里，经过了谁。 搞清楚这个，比记住任何一条结论都重要。

本文仅抓取本人自有账号、且仅在本机与本人设备之间进行，未使用 ARP 欺骗、中间人等手段获取他人流量。抓包文件仅保存在本地，未上传至任何公共平台。
